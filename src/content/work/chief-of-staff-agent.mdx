<Section title="Problem" fig="3 roles" figLabel="school, teaching, consulting">
I'm a dual-degree student, a teaching assistant, and a consultant. Most of what lands on me starts as a blank page, and the promises I make live in meeting notes, email, and chats with no single place to see them.

The job: start every piece of work from a draft and keep every commitment in one place, without the agent ever acting on my behalf.
</Section>

<Section title="How it works" fig="4×" figLabel="runs a day in the cloud">
<CosDiagram />

A small model splits each incoming note into items and classifies them; a mid-size model drafts replies, recaps, and first work blocks; a guardrail decides what is allowed to reach my accounts. It connects through MCP to Gmail, Calendar, Drive, my meeting notes, and Canvas.

<p class="note">Everything deterministic (time zones, free slots, dedupe keys, edit ratios) is plain tested code, never the model.</p>
</Section>

<Section title="My role" fig="AI native" figLabel="directing agents is the skill">
**I decided:** the problem and scope, "drafts, never sends," the switch from a block list to an allow list, delivery through my calendar instead of email to myself, outlines instead of drafts for graded coursework, the privacy boundaries, and where to trade recall for precision.

**AI built:** nearly all code, prompts, and tests, to my specs and under my review. I ran every real-data dry run and hand-labeled the eval sets.
</Section>

<Section title="Decisions and trade-offs" fig="0" figLabel="sends, deletes, or shares possible">
**Safety in code, not the prompt.** A hook blocks anything not on an allow list, including tools on connectors added later. The cost: some useful actions, like deleting a stale event, still need me.

**Precision or recall depends on what a mistake costs.** A missed promise breaks a commitment, so promise detection favors recall. A false style rule changes every future draft, so the edit learner favors precision.

**Real data over synthetic sets.** Every feature ran in dry-run mode on my real accounts before it could write anything.

**Outlines, not drafts, for graded work.** The original spec said to fully draft discussion posts. Where a course does not allow AI, that is an academic integrity risk, so the agent reads a per-course policy and writes outlines and work blocks instead.
</Section>

<Section title="Buy or build, now that assistants ship" fig="3" figLabel="always-on assistants launched this fall">

**What I'd buy.** If I started today, I'd buy the shell: triage, drafts, scheduling, and a daily brief. A product team maintains the connectors, and 7 of my 28 failures were connector quirks I had to fix myself.

**What I'd keep building.** The parts none of them guarantee in their launch docs: no path to send at all, student data that never reaches a log, and a promise ledger whose recall I measure. For a teaching assistant, those are requirements, not features.

**How I'd decide.** Not from launch posts. My real-data cases are an acceptance test: run the 28 failures and the 67-email promise set against a bought assistant in dry-run, and switch any capability where it matches mine. Head-to-head results: <Pending what="dry-run comparison" />

<Section title="If I were the PM at a lab" fig="Release gate" figLabel="real-data dry run before writes">
I'd ship agent tool permissions as default-deny, with a dry-run mode on by default, and make "run it on real data without writing" a release gate. Synthetic evals told me everything was fine; real data found 28 problems.
